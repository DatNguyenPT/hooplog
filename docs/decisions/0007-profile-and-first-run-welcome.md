# 0007: The profile is one local row, and the welcome screen shows once

Status: accepted (M1 profile and settings slice)

**Context.** The player needs a place to set their name and see how the app is set up, and a short first-run welcome, with no sign-in (the app is guest-first). The product owner has decided on English and metric units only for now, so there is no real choice of language or units to store yet.

**Decision.**
- A `profile` table (migration 5) in the same on-phone SQLite database as everything else. It holds at most one live row, enforced by the database with the same unique-index technique as the single open session and the single active plan. Columns: the optional display name (1 to 40 characters, also checked by the database), `onboarded_at` (when the welcome screen was finished or skipped) and the usual `id` (client-generated UUID), `created_at`, `updated_at`, `deleted_at`, so it syncs like every other table later.
- The row is created by the first save, never by a read. A fresh install has no row, and that reads as "no name, welcome not seen". A seeded row would need a fixed id that every install shares, which would collide once sync exists.
- No unit or language columns. Settings shows Units ("Metric") and Language ("English") as fixed, read-only lines. When a second option exists, a later migration adds the column and the line becomes a choice.
- The welcome is one screen, shown once: it says what the app does, that no account is needed and that everything stays on the phone, and asks for an optional name. "Get started" saves the name (if any) and marks it seen; "Skip for now" marks it seen without saving a name, even if something was typed. Both open Home. If saving fails the player stays on the screen with an error and can try again.
- The gate lives on Home. Home reads the profile; it shows the loading indicator until the profile is known (so a new player never sees Home flash by), redirects to `/welcome` when `onboarded_at` is empty, and greets the player by name when there is one. If the profile cannot be read, Home opens normally without a greeting: a database hiccup must never lock the player out of the app.
- Name rules are pure functions in `profile/domain/profile.ts`: trim, collapse repeated spaces, blank means no name, more than 40 characters is refused with a message (never silently cut). The welcome screen and Settings share them and the text field.
- Settings is a screen at `/settings`, opened from a button next to the title on Home. For now it edits the name, shows the fixed preferences and says where the data lives. Export/import and delete-all (the next roadmap item) will be added to this screen.

**Trade-offs.** Putting the gate on Home rather than in the app's root layout needs no shared state and no new navigation machinery. The cost is that only Home enforces it, which is fine because every other screen works without a name and nothing links into them from outside the app. A migration cannot be undone once it has shipped, but the table is tiny and its columns are nullable, so adding preference columns later is cheap. The owner's own phone, which already has data, has no profile row and will see the welcome once after updating, the same as a new install; guessing "this player is not new" from their logs would add a rule that is wrong as often as it is right. Showing units and language as fixed lines instead of switches is honest about what the app supports, at the price of no real setting yet.

**Consequences.** `docs/TECHNICAL_ARCHITECTURE.md` section 4 points here. The export in the next roadmap item should include the profile row. "Delete all data" will have to decide whether to remove the profile too; removing it would send the player through the welcome again on the next start, which is reasonable but should be a deliberate choice there. All text goes through the `welcome.*`, `settings.*`, `profile.*` and `home.greeting` / `home.settings` translation keys.
