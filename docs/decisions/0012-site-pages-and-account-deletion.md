# 0012: More site pages, password-checked account deletion, and unconfirmed accounts

Status: proposed (M1 slice 6 follow-up, 2026-11-02; the product owner asked for these after testing the merged accounts slice). Waiting for the owner's review.

**Context.** After the accounts slice was merged the owner reported that an account that was never confirmed still seemed to exist and to sign in. They also asked for a separate page for each thing Supabase or the stores need to link to (confirm an account, delete an account) and for the delete-account flow to be finished. [0008](0008-optional-accounts-supabase-auth.md) planned deletion as a system dialog with no password; [0011](0011-email-confirmation-page.md) built a single page.

**Decision.**

- **Unconfirmed accounts.** Supabase saves the user the moment someone signs up and marks it "Waiting for verification" until the email link is opened. That row cannot be avoided and is not a bug. What must hold is that nobody can sign in with it. With the dashboard's "Confirm email" switched on, Supabase returns no login at sign-up and refuses sign-in with "email not confirmed". The app adds its own safety net: a login for an account without a confirmed email is dropped and never shown as signed in. If "Confirm email" is off, Supabase confirms every account by itself, the app cannot tell, and that switch is the only lock. The owner's checklist is [SUPABASE_AUTH_SETUP.md](../SUPABASE_AUTH_SETUP.md).
- **Pages.** `site/` has four pages that share one stylesheet (`site/site.css`): the home page (Supabase's Site URL), `confirm/` (where the confirmation email sends the player), `delete-account/` (how to delete an account; the address Google Play asks for) and `account-deleted/` (a plain "Account deleted" page, not linked from anything yet). The home page and `confirm/` show the same three messages as in [0011](0011-email-confirmation-page.md), from the same script (`landing.js`); a test checks that their text stays identical. Every page keeps the 0011 rules: no requests to other sites, no cookies, no analytics, links relative to the page (the site lives under `/hooplog/`), and kept out of search results. `site/pages.test.js` checks all four.
- **Where the email sends the player.** Sign-up now passes `emailRedirectTo = <site>/confirm/`. Supabase honours it only if that exact address is on the Redirect URLs list (Authentication, URL Configuration). Otherwise it falls back to the Site URL, which shows the same message once the owner has set it to the home page. The site address is `https://datnguyenpt.github.io/hooplog/` unless `EXPO_PUBLIC_SITE_URL` says otherwise (for a domain of the owner's own, later). It must be https and carry no query or fragment; any other value is ignored in favour of the default, because the link in the email carries the player's login.
- **Deleting an account.** Settings, Account, Delete account opens a form on the same screen instead of a system dialog. It says what is removed and what stays on the phone, and asks for the password. The password is checked by signing in again, and only then does the `delete-account` Edge Function from 0008 run. A wrong password removes nothing. When it is done the phone is signed out and the sign-in form shows "Account deleted". The static `delete-account/` page describes these steps.
- **The password check protects the player, not the server.** It stops a stray tap, or someone briefly holding an unlocked phone, from erasing an account. A person who already holds a valid login could call the function directly without the password. Today that costs nothing, because an account holds no data (there is no sync yet). Before sync ships (M4) the function must check the password, or a very recent sign-in, itself.

**Trade-offs.**

- Confirming a deletion with a link in an email is stronger, because it proves access to the mailbox. It needs a custom email sender, an edited email template, page code that handles the login token (which loosens the no-other-sites rule for that page) and extra headers on the function. That is not worth it before there is data to protect. `account-deleted/` is the page such a link would end on.
- A player who forgot their password cannot sign in, so cannot delete. The app has no password reset (it would need its own page and a Redirect URLs entry). Google Play also wants a way to ask for deletion without the app. Both need a contact address that the owner chooses and publishes; none is invented here.
- The re-entered password is an ordinary sign-in attempt, so it counts against Supabase's limits on attempts, and it leaves a fresh login on the phone, which the deletion then ends.
- The pages are written by hand with no build step. Shared parts (the stylesheet, the page head, the two matching pages) are copied, and tests catch drift.
- All of it needs dashboard changes only the owner can make. Until the Redirect URLs entry exists, the email lands on the Site URL. Until the function is deployed, "Delete account" answers "This is not available yet".

**Consequences.** A new page is a new folder in `site/`, an entry in `PAGES` in `site/pages.test.js` and, if Supabase should send people there, an entry in the Redirect URLs list. `noindex` stays on every page until a store listing needs the delete page to be findable. Password reset and email-change pages are deliberately not built, because the app has neither flow. The beta preparation in the roadmap gains the deletion address and the contact address.
